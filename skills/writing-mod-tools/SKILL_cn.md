# 怎么写模组工具

> **置信度:** 这些规则在本仓库写工具的过程中**再次撞上**过,因而可信;它们引用的事故是引自原文,不是重跑出来的。

[English](https://github.com/YC426/HD2-Agent-Skills/blob/main/skills/writing-mod-tools/SKILL.md) / 简体中文

这些经验提炼自本工作区各模组中约 120 个工具：四个构建脚本、一个有守卫的部署器、十几个实时内存探针、日志分析器、离线模拟器，以及一个静态 FFI 审计器。下面每一条规则，都是其中某个工具做对的事情 —— 通常是在先做错之后。

读者是一个**已经有点恼火的陌生人**。他运行你的工具，是因为有东西坏了。它浪费掉的每一分钟，都是它失败的一分钟。

## 1. 写出前置条件，并且降级而不是崩溃

一个因为没装 `lupa` 就带着 traceback 死掉的工具，除了告诉用户你的工具很脆弱之外，什么也没教会他。

```python
try:
    import lupa.luajit21 as lj
except ImportError:            # 缺少的前置条件要降级，绝不能抛 traceback
    lj = None
...
if lj is None:
    print("note: LuaJIT check skipped (lupa not installed, or --no-luajit)")
```

然后说明**没有它时还有什么仍然可用** —— “另外五项检查不需要它” —— 这样这次运行仍然有用。把同一个开关显式提供出来（`--no-luajit`），让降级模式是可测试的，而不只是假设中的。

把前置条件写成一张表，列出缺失时的后果，而不是写成散文：

| 需要 | 为什么 | 缺失时 |
|---|---|---|
| Python 3.8+ | 运行该脚本 | — |
| `lupa` | 用真正的 LuaJIT 编译源码 | 跳过该项检查，并在输出中说明 |
| 游戏**正在运行** | 实时探针要读它的内存 | 以退出码 2 退出，并提示 "start the game first" |

把“必需”和“可选”明确区分开。只用于某个子命令的前置条件，应该写在那个子命令的帮助里，而不是放在文件开头。

## 2. 默认只读；必须写入时，要有守卫

这里大多数工具都是只读的，并在 docstring 里写明 —— 这是 `README` 级别的诚实：

> 只读：它用 `PROCESS_VM_READ` 打开游戏 …… 不会向游戏写入任何东西，
> 也不使用窗口或输入自动化。

对于任何会修改东西的工具，参照 `safe_deploy.py` —— 写这个部署器的*原因*，就是更早的一次构建硬编码了一个游戏槽位，覆盖了 mod loader，让整个安装里所有 Lua 模组都消失了。它的规则可以推广到任何会修改文件的工具：

1. **按内容识别目标，绝不按你记得的某个编号。** 它通过在层内部的 `-- HD2-Addon:` 声明来找到自己的槽位。对 loader 来说，“字符串搜索对身份识别毫无用处”，所以它改为用 SHA-256 匹配 envelope 字节。
2. **拒绝任何无法证明属于你的东西。** `classify()` 返回 `mine` / `foreign` / `missing`，而*未知*一律算作 `foreign`。
3. **先 `dry_run=True`**，打印出它会做什么。
4. **绝不挤占他者：** 还没有槽位时，就在当前最大值之上分配一个新编号。
5. **写入后校验**，然后重新校验其他一切都没有变，若有旁观者被移动，就大声失败（明确报错）：
   ```python
   before = {n: _digest(...) for n, p in layer_numbers().items()}
   ...
   for n, h in before.items():
       if n != target and _digest(...) != h:
           raise DeployRefused("slot %d changed during deploy - aborting" % n)
   ```
6. **给它一个能复现原始 bug 的自检**，并把它作为默认入口点运行。`safe_deploy.py` 的 `_self_test()` 会把历史上那个硬编码槽位重新喂进去，并断言它被拒绝 —— 这样回归就无法悄悄回来。

一个没有 dry-run、没有拒绝路径、也没有自检的变更工具，就是一个带 CLI 的走火枪。

## 3. 退出码和 `--json` 就是接口

人读摘要；脚本和 agent 读退出码。两者都要，永远如此。

- `0` 表示成功，非零表示失败，并且**把原因写到 stderr** —— 还要点名是哪个闸门：
  `FAIL refusing to build: user32 symbol(s) declared: GetCursorPos`。
- 当修复方式不同时，两种失败模式就应该用不同的退出码：“什么都没找到”（1）与“拒绝覆盖”（2）。
- `--json` 用于任何会被 agent 或 CI 消费的场景。要给它结构（`{"ok": false, "failed":
  1, "checks": [...]}`），而不是一大堵文本再硬接一个 JSON 开关。
- 打印一个可机器校验的页脚：字节数和 **SHA-256**。下一个人就是靠这个确认自己拿到的是你指的那个产物。

## 4. 让发现过程零成本，并且先找遍所有地方再开口问

`fetch_bingus_tools.py` 会搜索一个显式路径、每个已安装模组的 `scripts/`、`tools/` 和 `vendor/` 目录，以及这个 checkout 自己周边的位置 —— 然后，如果找到完整的一套，就打印出在哪里并停下，而不是去猜一个目标位置。`--list` 展示会发生什么，且不复制任何东西。

推广开来：需要某个文件的工具应该**先搜索显而易见的位置**，把找到的结果以表格形式报告出来，每个必需文件对应 `OK`/`--`，然后才去问。绝不要让用户去找一个你本可以定位的东西。

当工具确实需要一个你不能再分发的第三方产物时，不要把它打包进去 —— 改为从本地获取或按显式 URL 获取（`--url`，绝不自动），并告诉用户把来源记到他们的 notices 文件里。

## 5. 读产物本身，而不只是读你自己的成功消息

构建说“built OK”；这完全不能说明产物是否*正确*。`inspect_package.py` 的存在就是为了补上这个缺口，独立地检查 envelope：

- 结构（必需的成员都在、恰好一个归档、sidecar 文件）
- manifest 语义（GUID 确实是个 UUID、`Version` 是 1、声明的图标确实被打进了包）
- **二进制格式**（magic、条目数量、每个条目的类型、文件内的范围、头部长度与主体一致）
- **身份**（名称 → 哈希的映射能解析到一个真实条目）
- **来源**（`--source` 证明被打包的 resource 里包含你构建出的代码，且源码里的版本与文件名一致）

注意这个解析出来的细节：内嵌声明*并不*在 resource 的偏移 0 处，因为每个 resource 前面都有一个 8 字节的头。假设显而易见布局的校验器会报出假失败 —— 这个工具的初版就干过。

## 6. 值得为它单独写一个工具的失败

这里最好的工具，每一个都是在一次具体的、代价高昂的失败之后写出来的。把它当作你判断某个工具是否值得写的检验标准：

| 失败 | 工具 | 好在哪里 |
|---|---|---|
| 一个模组在加载时被**静默跳过**（LuaJIT 的 65535 条指令上限） | `build_mod.py` | 拒绝打包；闸门会点出这个限制 |
| 一个声明**挤掉了另一个模组的**并把它弄失效了 | `ffi_audit.py`、构建闸门 | 精确的规则，以及违规符号的清单 |
| 一个模组**连续 165 个会话毫无动静** | `analyze_vehicle_cooldown_log.py` | 逐阶段报告，于是“什么都没做”变成“停在 locate 这一步” |
| 某个探针的地址链在实时环境下不可读 | `check_live_probe.py` | 交叉核对两个独立来源（模块列表*和*探针自己的头部解析），不一致时把两者都打印出来 |
| addon 自身的计时不可用 | `measure_overhead.py` | 解释*为什么*：`os.clock()` 的分辨率约 15.6 ms，所以亚毫秒级的工作会被舍入成 0.000；改为从外部测量 |
| 一个硬编码的槽位删掉了 mod loader | `safe_deploy.py` | 按内容定位目标、dry-run、拒绝、写入后校验、自检 |
| **7 轮实时验证，其中 2 轮有信息量** | `ability1_live.py` / `ability1_mask.py` | 见 §6b：消耗掉其余轮次的是判据和工具（instrument），而不是假设 |

所以：**为你刚刚付出代价的那个失败写工具**，并把那次失败记进 docstring。这样下一个人就知道这个工具为什么存在、什么时候该用它。

## 6b. 先验证判据和工具（instrument）

**这是本工作区里代价最高的一课。** 一个工具可以是正确的、运行成功的，却什么也证明不了 —— 因为它用来判断“我的改动已经生效”的*判据*是错的，或者因为采样闸门从未打开。

在某个下午针对单个功能的实时工作（`LIVE-EVIDENCE-2026-10-04.md`）中：**七轮实时验证，只有两轮真正测试了假设。** 其余的则消耗在错误的判据、学错的值、或坏掉的工具（instrument）上。在一个精心搭建的测试台上，这是 5/7 的浪费率，而每一次都是可以避免的。

### 记录：真正消耗掉这些轮次的是什么

| 轮次 | 报告的结果 | 真正的原因 |
|---|---|---|
| 1 | 三次触发，用户没有移动 | **判据错了** —— 回退的“学习”把 *sprint* 记录绑定成了 *prone* 记录，所以触发来源是 `Shift`，而不是 `Z` |
| 2 | 零次触发 | **判据错了** —— 它要求状态位 75 **和** 79 同时置位；在实时环境中它们是各自独立闪烁的 |
| 3 | 6 次干净的触发，`total writes=0` | **工具错，两处** —— 见下；两处缺陷都表现为静默的 `zero writes` |
| 4 | 触发生效了，写入了 20 字节，用户仍然没有移动 | 假设真的被证伪 —— **四轮中唯一有信息量的失败** |

Round 3 的两处缺陷值得记住，因为它们看起来都像一个正确的否定结果：

1. **不带 `Ex` 的地址空间误判。** `VirtualQuery` / `VirtualProtect` 作用于*调用者*进程。从游戏外部调用时它们会把游戏的一个堆地址报成 `MEM_FREE`（13:09 那次记的是 `page not committed`），于是写入从不发生。跨进程必须用 `VirtualQueryEx(handle, …)` / `VirtualProtectEx(handle, …)`。
2. **句柄没有写权限。** 既有的*读取器*句柄是用 `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` 打开的。于是 `VirtualProtectEx` 毫无解释地失败（13:10 那次记的是 `VirtualProtectEx failed`），因为它需要 `PROCESS_VM_OPERATION` —— 而 `WriteProcessMemory` 还需要**再加上** `PROCESS_VM_WRITE`。正确的集合是 `0x0400 | 0x0010 | 0x0008 | 0x0020`。

把只读句柄复用到写路径上是范畴错误，而且除非你专门去看，它不会报“权限不足”，只会报“什么都没写进去”。

### 由此得出的规则

1. **从未打开的闸门不是否定结果 —— 它是一个没被测试过的工具。** 要在*日志里*区分“假设失败了”和“我的触发从未发生”，否则你会把后者当成前者来报告。每次检查都要打印闸门自身的输入。
2. **学到的/发现的值，在被独立验证之前都不是证据。** 把“工具学到的内容”当作行动的前置条件，意味着一次糟糕的学习会无声地让实验失效。先用一个独立信号验证该值，并把投票计数记进日志，这样 1/1 和 20/20 看起来就不一样。**如果学习连续六轮都失败（它确实失败了），就别再改进学习器，改用一个确定性的读取替代它。** `find_key_state.py` 就是这样：按住空 / 按住该键 / 松开，三次快照做差分，只报告*仅*在中间那次变化的偏移量 —— 不学习、不启发式、不依赖会话。**把测量变成确定性的**，几乎总是好过**把推断变聪明**。
3. **采样索引是会话范围内的。** 在一个会话里是 `19, 95, 207` 的记录，到下一个会话里就不一样了，而过期的学到的值（learned value）集合看起来合理却是错的。绝不硬编码索引，并在每个会话开始时重新验证。
4. **每次跨越进程边界时，都要检查你对地址空间的假设。** 查询、保护和读取都有非 `Ex` 形式和 `Ex` 形式，而非 `Ex` 形式隐含的意思就是“我自己的”：`VirtualQuery` / `VirtualProtect` 作用于调用者进程，`VirtualQueryEx` / `VirtualProtectEx` 接收目标句柄。使用非 `Ex` 形式的跨进程工具，给出的是一个关于错误进程的真实答案。**而且写路径需要带写权限的句柄** —— 复用一个只读句柄会让 `VirtualProtectEx` / `WriteProcessMemory` 失败，其表现是“零次写入”，不是“权限不足”。见踩坑清单 §5。
5. **单次写入不是持久写入。** 该功能只清除了一次状态；而在实时环境中，游戏**每一帧**都会重算它，所以那次清除在 50 ms 之内就被覆盖了。“一次写入只发生一次”这个早先的证据来自另一条代码路径（站着不动 vs 真的在跑）。**在你将要交付的条件下测试这个机制**，并且比起“我的写入成功了吗？”，更要问“N 帧之后我的写入还在吗？”。
6. **在走上实时验证之前，先在离线环境证明信号存在。** 一次验证运行要花掉一次部署和一次重启；一个检查器只要几秒钟。如果判据可以对着一份录下来的日志或一个抓下来的缓冲区求值，就先在那里做，然后再用实时运行去测试假设，而不是测试管道。
7. **两个工具必须达成一致的任何事，只能有一份实现。** 随 `hd2-mission-entry` 一起发布的输入工具里，两个调用方各自决定“哪个窗口是游戏” —— 其中一个拿*类名*字段去比，却在读*标题*字段，于是那个检查永远不会失败。修法是让两者共用一个 `game_window()`。重复的判据会静默漂移；共享的入口点只需要测一次。

### 任何实时验证运行之前的两行自检

```text
1. 我能在日志里说明判据触发了 —— 且与效果无关吗？
2. 如果答案是“什么都没发生”，我的工具能告诉我它属于哪一种吗：
      判据从未匹配 | 匹配了但没有写入 | 写入了但没有效果？
```

如果任一答案是“否”，就先去修工具，再花这次运行。一次无法区分这三种结果的运行不是实验；它是一次带日志文件的抛硬币。

## 7. 注释承载证据

docstring 就是昂贵知识所在的地方。这里写得好的那些读起来像事故报告：

```python
"""HD2 Arsenal / Bingus 模组的带守卫 envelope 部署。

这个文件为什么存在（2026-10-01，用户报告 "加上这个模组后会让所有lua模组直接不生效"）：
    build121.py ... 把 ... envelope 写进了一个硬编码（HARD-CODED）的游戏槽位 ...
    覆盖它会删掉 mod loader，于是整个 Lua 生态都死了 ...
"""
```

要包含：日期、用户报告的症状原文、机制，以及由此得出的规则。不要写“处理了边界情况”这种话 —— 那对谁都没有信息量。

还要写明这个工具**做不到**什么。`ffi_audit.py` 说得很直白：它是一个正则扫描器，抓不到通过宏或 typedef 到达的符号，而一个与别的模组相似的声明，只会针对它已知的符号做检查。诚实写出做不到什么，才让一个工具值得信任。

## 8. 测试工具本身，包括失败路径

- 在测试里跑通失败路径：构建脚本的闸门是通过声明一个已知的坏符号、并断言退出码非零来演练的。
- 当工具声称带来改进时，优先用**差分**检查：“原始 189 次读取，adapter 53 次，每个观测到的字段都一致”是可验证的；“更快”不是。
- 让工具自己的结论可复现：输出能复现它的那条命令，并把 fixture 纳入版本控制。

## 9. 交付工具时要带上它的结论，而不是一句声称

- 在摘要里放上退出码和产物哈希。
- 说明哪一部分是**已验证的**、哪一部分**不是** —— 用假输入测过的工具，不等于用真实对象测过的工具。这两个事实都该写进 README。
- 当某项检查被跳过时，要在输出里说明。静默跳过会被读成通过，而这是校验工具可能有的最危险的行为。

---

## 工作流

1. 说出这个工具为之存在的那个失败，带上它的日期和症状。
2. 决定是只读还是修改。修改 ⇒ dry-run、按内容定位目标、拒绝路径、写入后校验、自检。
3. 先写 docstring：前置条件、它检查什么、它做不到什么。
4. 用 `argparse` 实现 `main()`，带上真实的前置条件、`--json`、有意义的退出码，以及哈希/大小页脚。
5. 为每个可选的前置条件加上降级路径，以及一个强制走该路径的开关。
6. 加一个测试，跑通它当初被写来捕捉的那个失败。
7. 在随它一起交付的 skill 或 README 里写明已验证/未验证的划分。

## §6b 的证据来自哪里
