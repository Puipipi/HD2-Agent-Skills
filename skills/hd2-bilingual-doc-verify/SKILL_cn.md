# HD2 双语文档校验

[English](https://github.com/YC426/HD2-Agent-Skills/blob/main/skills/hd2-bilingual-doc-verify/SKILL.md) / 简体中文

> **置信度:** 已在本地验证；它的两种失败模式都是被刻意触发的。

`scripts/verify_translations.py` 检查的是翻译**不**该改变的那些东西，这样评审的注意力就能
放在文字上，而不是放在某个代码示例是否仍然正确上。

它是在本仓库为每份文档都长出一中一英一对之后写的：六对 `X.md` / `X_cn.md`，其中中文副本里
一个过时的代码块，是没人会注意到的缺陷。

## 前置条件

| 需要 | 原因 | 缺失时 |
|---|---|---|
| Python 3.8+ | 脚本 | — |
| **`lupa`** | 在真实 LuaJIT 上重新编译翻译后的 Lua 块（检查 1） | 另外五项检查照常运行；脚本会打印出它跳过了什么 |
| 处于某种仓库布局中的文档对 | 发现逻辑会在树的任何位置找出旁边有 `X_cn.md` 的任何 `X.md` | 用 `--root` 指定位置 |

别的什么都不需要：不需要游戏、不需要加载器工具、不需要网络。它不写任何东西。

## 用法

```powershell
python -B scripts/verify_translations.py                     # 扫描仓库根目录
python -B scripts/verify_translations.py --root <repo>       # 或者指向某一个仓库
python -B scripts/verify_translations.py --no-luajit         # 强制进入降级模式
```

退出码 0 = 每一对都通过；非零 = 至少有一对失败，并会点名是哪一对。

## 九项检查

1. **翻译后的 Lua 仍能在 LuaJIT 上编译** —— 从*译文*中提取每一个 `lua` 围栏并编译它。
   抓住动过代码的翻译。
2. **去掉所有注释之后，代码围栏与源文件一致** —— Lua 用 `--` 和 `--[[ ]]`，shell/PowerShell
   **和 Python** 用 `#`（行内的 `# …` 注释是可翻译文本），伪代码用 `;`。注释*会*被翻译；
   代码不会。
3. **文档型围栏按文档来比较** —— 当一个围栏没有可执行代码时，它就算作文档，即：目录树 /
   包布局、一段 `text` 散文块，或者只引用了 docstring 或注释的代码围栏。目录树按骨架比较
   （字形、缩进、每行的第一个 token），这仍能抓住丢掉的分支或被改名的路径；散文只按行数
   比较，因为每个词都被翻译过。
4. **标题结构一致** —— 按顺序比较数量与层级。抓住被丢掉的小节。
5. **每个相对链接都被带过去**，或者被有意改指到 `_cn` 同类文件（作为提示报告，不算失败）。
   源文件指向译文*本身*就是的那个 `_cn` 文件，也算一条提示。
6. **frontmatter 完好** —— 键相同，`name:` 不变（它是标识符），`description:` 已翻译（它是
   读者选择技能时看到的东西）。
7. **语言切换行存在、只有一条，并指向对侧** —— 在双方的头块里，当前语言不加链接：
   ```
   English / [简体中文](https://github.com/YC426/HD2-Agent-Skills/blob/main/README_cn.md)
   [English](https://github.com/YC426/HD2-Agent-Skills/blob/main/README.md) / 简体中文
   ```
   绝对 URL 是有意为之 —— 抄自 DeepSeek 自己的仓库，因为切换行是读者在能导航到别处之前
   唯一需要的那个链接。它被检查而不是被信任：删掉一条、指向错误的文件、或者在头块里留下
   两条，都会让本次运行失败。

8. **每个 skill 文件都自带切换行,即使还没有译文** —— 对 `skills/` 下每一个 `SKILL.md` 与
   `SKILL_cn.md` 单独检查,与配对无关。配对循环只在两侧都存在时才运行,所以"有英文、暂无译文"的 skill
   会完全逃过检查:这正是五个英文 skill 丢了切换行、而它们的中文文件却有切换行的原因。
9. **GitHub 绝对链接的目标必须能解析** —— 由 `check_absolute_targets()` 报告。因为切换行按惯例
   用绝对 URL,而对侧缺失时渲染出来就是死链,别的检查都发现不了。

## 烘焙在其中的两个教训

- **一个假设了显然布局的校验器会报出假的失败。** 第一个版本只剥掉整行注释，于是每个含有
  行尾 `--` 注释的代码块看起来都不一致。修校验器而不是修翻译，才是正确的选择 —— 而这一点
  之所以显而易见，只因为失败数量高得离谱。同样的事情后来又发生了两次：**Python** 围栏里
  的一处行内 `#` 注释（剥离器只认识 shell），以及一个**只引用 docstring** 的 `python` 围栏
  （完全没有可执行代码，因此整块都是散文）。每一次修复都让检查 3 更窄也更真实：*把代码当
  代码比，把文档当文档比，并且从内容而不是从围栏标签来判断。*
- **检查 3 的存在同样源于一次误报。** 某个新技能里的四个“代码”围栏其实是目录树；把翻译过
  的注解当作代码改动，会逼着译者把散文留在英文里。

**当校验器报出失败时，先看失败本身，再动翻译。** 上面三种情况里，翻译都是对的 —— 包括那个
“代码”其实是一段解释部署事故的 docstring、并且是有意翻译的那次。一个出错的 linter 比没有
linter 代价更大：它教会人们忽略它。

## 局限

- 它证明的是**结构**上的对应，而不是翻译*正确*。一个译错的句子能通过每一项检查。散文还是
  要人去读。
- 检查 3 的结构指纹按设计忽略注解文本，所以一个把路径描述换成错误内容的翻译不会被抓住。
- 它只认识 `discover_pairs()` 里的那些布局；组织方式不同的仓库需要扩展那个函数。
