# HD2 game event identification

English / [简体中文](https://github.com/Puipipi/HD2-Agent-Skills/blob/main/skills/hd2-game-event-identification/SKILL_cn.md)

Use this skill to identify **what happened and what object it referred to**. It ends at a normalized event; message templates, role permissions, queues and cooldown policy belong to the neighboring [`hd2-event-chat-automation`](../hd2-event-chat-automation/SKILL.md) skill. For table layout and resource hashing, use [`hd2-offline-data-workflow`](../hd2-offline-data-workflow/SKILL.md). For a narrowly scoped external read-only address check, use [`hd2-live-memory-probe`](../hd2-live-memory-probe/SKILL.md); for the player's selected language, use [`hd2-game-language-autodetect`](../hd2-game-language-autodetect/SKILL.md).

## Evidence and scope

The concrete reference implementation is [HD2-AutoChat commit `4445596a76ed387edc3c09d0d25aa9d06ffd5b11`](https://github.com/Puipipi/HD2-AutoChat/tree/4445596a76ed387edc3c09d0d25aa9d06ffd5b11). The runtime observations in that implementation are gated to one Steam build and `game.dll` fingerprint. Its catalogs combine current-build component exports, resource paths and localization data; those community exports are useful evidence, not official source code or a promise of complete future coverage. The evidence is mixed: static current-build data, offline fixtures, source-level validation, and one user-confirmed live cache-mark capture. Do not describe an offline fixture as an in-game confirmation or generalize the one capture.

## Identification workflow

1. **Keep producers separate.** A HUD ping ring and a tactical-map pin are different producers. The reference reader gets map pins from replicated actor state because the Map21 receiver returns before it inserts a HUD ring record; it reads the ordinary HUD ring separately. Similar marker materials do not prove a shared event kind. See [the producer notes and reader](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L39-L46) and [map/ring snapshot code](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L717-L770).

2. **Preserve identity fields separately from display text.** Carry the creator/actor, producer `source`, action, native kind and localization key, stable target/entity ID, resource hash, category, position and session/scene identity as distinct fields. A localized string is presentation evidence; it is not a substitute for an entity ID or resource identity. Resolve a map target through its network identity to the current entity, then to its resource identity. Resolve mission-objective text through the current objective manager and runtime name override where available. The reference path is [objective name resolution](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L783-L817) and [map target resolution](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L839-L868).

3. **Require evidence before assigning a target or category.** Empty terrain, an empty map-pin type, an invalid/self target ID, and an unknown resource paired with a generic label do not identify a special location. A ground-style marker is accepted only for a reviewed mission target. Generic terms such as “Special location”, “Objective terminal”, “Enemy unit” or “Supplies” may be native fallback labels; they do not turn an unknown object into a building, enemy or pickup. Keep unresolved names generic or drop the event according to the producer contract; never invent a specific target. See [target gates and fallback handling](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L819-L870) and [unknown-target handling](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L947-L1008).

4. **Use current-mission data for objective roles.** Resource identity can tell you that an object is a mission site; it cannot establish whether it is the active primary, prerequisite or optional objective. The reference obtains importance from the current objective runtime and maps only known importance values; unknown stays `unknown`. Never infer main/side importance from a name, map label or static resource catalog. The reviewed mission catalog marks generic/non-specific entries and records its data version and source hashes in [`mission-targets.json`](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/docs/mission-targets.json).

5. **Keep buildings, pickups and mission shells distinct.** Reviewed mission buildings include things such as illegal broadcast towers, extraction beacons, command bunkers and Super Earth flagpoles. The CQC-1 One True Flag is a carried weapon, not the mission flagpole. Ammo, stim, grenade and sample pickups use a separate `supplies` category and can be independently disabled; do not classify them as buildings. For SEAF artillery, six resource identities are supported as ObjectiveShells, but two identities do not prove which shell variant they represent. Require a specific native label for those ambiguous variants; otherwise leave them unresolved or suppress them. See the [special-target evidence](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/special_targets.lua#L1-L24), [supply and generic-name sets](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L486-L516), and [supply option](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/auto_chat.lua#L9397-L9404).

6. **Treat contextual labels as narrow evidence.** The `0ABED3586E397289` Super Earth cache / Salute drop-pod fallback is based on one sanitized live direct-target capture plus a matching static asset path. Its source explicitly says this is contextual, not an official localized name, and must not be generalized. There is no verified evidence here that a bunker cannot be marked, nor a general rule that all “Salute” or bunker objects resolve the same way. Preserve that as an open question until a target-specific capture or authoritative component evidence resolves it. See [the scoped exception](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/special_targets.lua#L13-L21).

7. **Separate a call-in from a mark, and observe non-marker successes independently.** In the pinned reference build, a stratagem call-in mark requires `kind == 20`, duration `9999`, and native flag `0x2000`; the displayed name or marker kind alone is insufficient. Preserve `action='summon'` versus `action='mark'` and distinct sources. Some mission stratagems/actions do not create a HUD marker. A separate activation observer detects changed per-peer activation records; its initial snapshot is a baseline, and cooldown-only changes are not fresh successes. Keep the two producers distinct and deduplicate each using its own source evidence. **A spawned entity or target's presence is not proof that a particular player successfully summoned it; without call-specific HUD evidence or a changed activation record that supports actor attribution, emit no actor-attributed call-in event.** These bits, layouts and offsets are build-bound, not portable ABI. See [call-in classification](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/ping_events.lua#L872-L905), [activation observer and baseline](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/stratagem_events.lua#L1-L10), and [success transition handling](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/stratagem_events.lua#L135-L194).

8. **Deduplicate by producer lifecycle, not by target name.** For a ring slot, use its observed token and age reset to distinguish an active mark from a new mark; harmless position/flag changes on a non-map mark should not resend it, while a reping after age reset is a new event even for the same target. A map pin's replicated pin state has its own identity/lifecycle; the reference treats a changed map position as a new mark. Mission activation events use the stratagem ID plus activation time within the observed session/peer record. Do not replay events that exist only in the initial baseline. Tests that pin these distinctions are [ring and map dedupe cases](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/work/standalone/tests/test_ping_events.py#L779-L799) and [mission-activation cases](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/work/standalone/tests/test_stratagem_events.py#L59-L75).

9. **Separate canonical identity from localized names and UI grouping.** Keep stable stratagem ID, native localization keys, canonical/debug identity, Chinese/English display names, icon material hash and UI color/family as separate fields. Red/blue/green UI grouping is not `beacon_color`—that enum has no green value—and icon hashes are materials, not target identity. Unknown catalog names should remain an explicit unknown/ID fallback rather than borrowing a similar translation. “Super Earth Flag” is a mission stratagem name; “CQC-1 One True Flag” is a different equipment item, confirmed separately in the [name audit](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/docs/STRATAGEM-NAMES-AUDIT.json#L635-L649) and [CQC-1 audit entry](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/docs/STRATAGEM-NAMES-AUDIT.json#L2375-L2390); the mission-catalog test also rejects the melee flag as the flagpole ([test](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/work/standalone/tests/test_mission_catalog.py#L23-L27)). Use the [stratagem catalog](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/stratagem_catalog.lua#L67-L86) and [catalog row construction](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/src/stratagem_catalog.lua#L122-L145).

10. **Classify flight as an independent movement trait.** First establish hostile faction and a valid enemy/resource identity. Then check the evidenced flying components before routing by `UnitSize`; a flying unit may be small, medium, large or massive. `UnitSize` is not armor or threat. A catalog generated from current component exports can make new known resources visible, but it does not prove that every future enemy, mission spawn or native ping producer is covered. Unknown IDs stay unknown; do not default to medium or infer flight from a name. The [coverage report](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/docs/ENEMY-COVERAGE-0.8.0.md#L9-L11) distinguishes current export coverage from official completeness; its [classification and generation limits](https://github.com/Puipipi/HD2-AutoChat/blob/4445596a76ed387edc3c09d0d25aa9d06ffd5b11/docs/ENEMY-COVERAGE-0.8.0.md#L57-L98) are essential context.

## Confidence and validation

Record each claim as one of: **static export/path evidence**, **offline fixture evidence**, **source-level build-pinned observation**, or **target-specific live capture**. State the exact game/data revision and DLL fingerprint for native offsets, flags and layouts. A successful offline fixture validates the parser against its fixture; it does not prove live producer behavior or complete coverage.

For each producer, include negative cases in the offline suite: empty point, generic label with unknown identity, invalid/self target, unsupported map type, same active mark polled twice, reping of the same target, map-pin position change, baseline snapshot, cooldown-only activation change, ambiguous shell identity, friendly/non-spottable enemy and missing localization. A field report must name the producer, build, source token/ID, target resource, localization key/value and disposition so a failed classification is reproducible.

The identification layer is complete when each emitted event retains its producer and actor, action, stable identity (or an explicit unknown), category, display-name provenance and dedupe token, and each unsupported or ambiguous case has a tested unknown/drop outcome. Then hand the normalized event to the chat-automation layer without embedding message, role or cooldown policy here.
