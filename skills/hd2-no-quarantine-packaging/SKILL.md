# Packaging a mod so its helper scripts are not quarantined

English / [简体中文](https://github.com/YC426/HD2-Agent-Skills/blob/main/skills/hd2-no-quarantine-packaging/SKILL_cn.md)

> **Confidence:** the mechanism is read from SmoothBoot's source, not reproduced. The build gate that refuses a script-bearing archive *is* verified here.

A mod that needs the user to run *something* — a log collector, a config picker, an exclude
tool — has a packaging problem: **mod sites quarantine archives that contain script files**,
and a quarantined release looks to the author like a mysterious rejection or a mod that
"uploaded fine" but nobody can install.

SmoothBoot solves it by never shipping the script. This skill is that pattern.

## The rule

> The archive contains **no `.bat` and no `.ps1`**. The mod writes the helper into the user's
> own config directory on first run, and the shipped in-game README tells the user where it is.

Both halves matter: an archive with no script passes scanning, and a helper that appears in a
predictable local folder is still discoverable. The user experience is unchanged; the upload
is clean.

## Why runtime generation passes where shipping does not

| Shipped in the ZIP | Generated on the user's disk |
|---|---|
| A scanner can unpack and inspect it before anyone runs it — this is exactly what site scanning does | The file does not exist at scan time |
| An unknown `.bat` from a download is the classic malware shape | It is created by a program the user already chose to run |
| It is part of the artifact you uploaded, so a false positive blocks the release | It is a local artifact, like a config file |

This is not evasion of a scanner: the generated file is **plain, readable PowerShell with no
obfuscation**, and the mod says so in its notices file. It avoids the *download-shape* false
positive, not detection.

## How SmoothBoot does it

In `mods/smoothboot/work/standalone/smoothboot.lua`:

```lua
local dir = HOME .. 'SmoothBoot/'          -- %LOCALAPPDATA%\CowboyBingus\Helldivers2\SmoothBoot\
local function wr(n, c)
    local f = io.open(dir .. n, 'w')
    if not f then error('cannot open ' .. dir .. n) end
    f:write(c); f:close()
end
...
wr('README.txt', readme)                   -- the guide, extracted from the source
wr('Collect-Logs.bat', [===[@echo off
rem Generated by HD2 SmoothBoot; run with the game closed.
chcp 65001 >nul
setlocal
tasklist /FI "IMAGENAME eq helldivers2.exe" 2>nul | find /I "helldivers2.exe" >nul
if not errorlevel 1 (
  echo Close the game first / Please close Helldivers 2.
  pause
  exit /b 1
)
powershell -NoProfile -Command "..."
]===])
```

Details worth copying:

- **Plain Lua `io.open(path, 'w')` + `EnsureDirectory`** — no shell is spawned to create the
  file or the folder. (Spawning a shell from the update thread has hung the game in this
  workspace; see the failure catalog.)
- **Provisioned once, guarded, and retried a bounded number of times**, not every frame: the
  caller tracks `tool_attempts` and stops after a few tries.
- **The generated batch is defensive**: it checks whether the game is still running and
  refuses with a clear message, sets `chcp 65001` so its own output is readable, and uses
  `-NoProfile` so a user's PowerShell profile cannot change behaviour.
- **The README is generated the same way, from the source**, and the shipped `README.txt`
  inside the archive is extracted from that same source string. One source of truth, so the
  in-game guide cannot drift from the code.
- **The archive's own build script enforces it**, with the reason in the code:
  ```python
  # no loose .bat inside the archive (Nexus quarantines script files) - the
  # companion tool is provisioned at runtime next to config.txt.
  ```
- **The notices file explains it**, so a reviewer or a user can see why a mod that "collects
  logs with a .bat" does not contain one.

## Making it discoverable

Generating the file is only half of it — the user has to find it:

- Say the exact path in the mod's in-game README and on the release page
  (`%LOCALAPPDATA%\CowboyBingus\Helldivers2\<Mod>\Collect-Logs.bat`).
- Note that it appears **after the first run**, not at install time.
- Log the fact at that level when it is written:
  `companion tools ready: <HOME>SmoothBoot/Collect-Logs.bat`.

## When you do want to ship a script

Sometimes the helper is the point (a standalone patcher, an installer). Then:

- Ship it as its own release rather than inside the mod archive, so a quarantine cannot take
  the mod down with it.
- Say plainly what it does and that it is un-obfuscated, and keep the source in the repo.
- Expect the first automatic scan to still be a false positive sometimes; plan a manual review
  path instead of re-uploading and hoping.

## Keeping the generator honest

The helper's *source of truth* is the mod source, not a stray file on your disk — otherwise
the generated copy and the version you test diverge. SmoothBoot carries a small tool for this:

```python
"""Replace the embedded, readable collector. No BAT is shipped in the ZIP."""
# work/tools/update_smooth_collector.py -- rewrites the embedded string in the mod source
```

Edit the helper through that tool (or through the source string yourself), never by editing
the generated file in `%LOCALAPPDATA%` — that copy is overwritten on the next run.

## Verify before you upload

- Unzip your release and confirm **no `.bat` / `.ps1` / `.cmd` / `.exe`** is in it:
  ```powershell
  python -c "import zipfile,sys; z=zipfile.ZipFile(sys.argv[1]);
  bad=[i.filename for i in z.infolist() if i.filename.lower().endswith(('.bat','.cmd','.ps1','.exe','.vbs'))];
  print('script-like entries:', bad or 'none')" Your-Mod.zip
  ```
- Run the game once, then check the helper was actually created where the README says.
- Keep the extraction check in your build gates so a later change cannot quietly add one back.

## What this does not solve

- It does not make a genuinely malicious or genuinely detected file pass. If the *mod* itself
  is flagged, the generated helper is irrelevant.
- It does not help archives that are flagged for another reason (bundled third-party binaries,
  an unsigned executable, a checksum clash with something known).
- A user's own antivirus may still flag the generated `.bat` on their machine when they
  double-click it. Say up front that everything it does is readable, and keep it short.
