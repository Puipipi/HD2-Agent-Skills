# 实战手册：什么会搞死一个 HD2 Lua 模组，以及怎么区分它们

[English](https://github.com/Puipipi/HD2-Agent-Skills/blob/main/docs/hd2-mod-failure-catalog.md) / 简体中文

写给要写 Helldivers 2 模组的人（Bingus/MDL 加载器，LuaJIT FFI）。下面每一条都是
**症状 → 根因 → 修法**，来自真实的失败尝试，主要取自本工作区的自定义护甲 2.5.10 与
SmoothBoot 开发日志。目的很简单：让你**认出**这个故障，并且知道在花掉整个周末之前
该先记哪些日志。

先读 §1。那是本页最贵的一条。

> 英文原文：[hd2-mod-failure-catalog.md](hd2-mod-failure-catalog.md)

## 1. `pcall` 不抓原生崩溃

**这是最花时间的一条规则。** `pcall` 只拦 Lua 错误。错误的指针、空的引擎槽位、错误的
原生调用不会抛 Lua 错误——它在 `game.dll`/`ntdll` 里 fault，连进程一起带走。

观察到的形态：

| 形态 | 看起来像什么 | 例子 |
|---|---|---|
| `ntdll 0xc0000026`（`STATUS_INVALID_DISPOSITION`）每隔几秒重复，帧回调死掉 | 游戏还在跑，但你的模组再也不会 tick | 在引擎建好字体/材质库之前调 `World.create_screen_gui` |
| `APPCRASH` 在 `game.dll`，日志里有个地址 | 硬崩回桌面 | 用未经校验的 id64 调 `G.set_scalar` / 材质参数 |
| 静默停止 | 日志在函数中间直接结束，后面什么都没有 | `pcall` 里的某个原生调用“返回”了，但再也没回来 |

对写模组的直接影响：

1. **绝不要靠“调一下看行不行”来试探引擎。** 用你已经掌握的**正向事实**做守卫（world 已
   解析、资源槽非 NULL、build 已校验），否则就跳过这一帧。
2. **守卫必须是取值判断，不能是 `pcall`。** `local ok = pcall(f)` 完全没告诉你 `f` 能不能
   安全调用；`if slot ~= nil and slot > 65536 then ... end` 才告诉了你。
3. **把工作排序，让不安全的部分在最后。** 读 → 校验 → 再调用。
4. **每次危险调用之前先写日志，不是之后。** 崩溃前那一行是你唯一的证人。这里好几个故障
   纯粹是靠“日志停在这个字符串上”定位出来的。

## 2. 时序：引擎还没建好

引擎是分阶段起来的。下面每一条都是观察到的真实失败。

| 症状 | 根因 | 修法 / 证据 |
|---|---|---|
| `ntdll 0xc0000026` 循环；日志停在 `building the panel` | 在字体/材质库存在之前调 `World.create_screen_gui` | 把所有面板工作推迟到**舰船 world 解析之后**（护甲模组实测约第 600 帧解析）。`held - ship world not resolved yet` 只记一次，不要每帧记 |
| 读引擎槽位时 `Attempt to index a nil value` | 即使管理器指针有效，**资源槽**早期仍是 NULL | **重试**，不要记死。护甲模组早期失败一次就整局放弃了面板，后来改成每 600 帧重试 |
| 面板在舰船上正常，进军械库就看不见 | 军械库是另一个/原生界面，为舰船建的保留式 GUI 在那里不显示 | 监听原生界面 id 变化并重建（见 §3） |
| 语言/字体测量什么都返回不了 | 字体库比启动更晚建好 | 把“测不出来”当成**要重试**，永远不要当成“不支持” |

规则：**任何依赖引擎库的东西都必须按帧预算重试，并且第一次成功必须记日志**
（`drawing resources acquired on try N`）。如果你在启动时记死了失败，就会在某些机器上
发布一个整局都是死的模组。

## 3. 保留式 GUI：面板“消失”有三个不同原因

`create_screen_gui` 返回的是一个**保留式**对象：引擎会一直画它的图元，直到你销毁它。
这带来三种不同的失败模式，但**用户看到的症状完全一样**：

1. **你让签名失效了，但再也没重建。** GUI 被销毁，而绘制路径没有再次运行。
2. **图层是旧的。** 保留式 GUI 会一直在**建它时**那个图层上绘制。所以在配置里改 `layer`
   必须触发重建——运行时改图层是**没用的**（护甲模组：`ui: draw layer -> N (panel redraw requested)`）。
3. **别的界面画在你上面。** 军械库会画自己的一层全屏。早于军械库打开而建的面板，这一趟
   进去就**永远**压在它下面（护甲模组：`ui: native screen X -> Y ... (panel redraw requested)`）。

修法：

- 在**全部**这些情况下失效：开关、分辨率、语言、绘制图层、原生界面 id，以及任何会改变
  布局的状态。
- 在该显示的地方重建 GUI，并且清空时**销毁你在每个 world 里拥有的每一个 GUI**（军械库
  那条路径会每个 world 建一份）：
  ```lua
  for _, entry in ipairs(PANEL.draw_guis) do
      pcall(sr.World.destroy_gui, entry.world, entry.gui)
  end
  ```
- 如果你是**每帧**失效而不是按状态失效，就会每帧分配并销毁一个 GUI。测它：两帧必须只建
  **一个** GUI。
- 离线就可以测，用 `lupa`，见 §9 的测试台说明。

**不要在你不拥有的 world 里分配 GUI。** 那个实验导致过一次原生崩溃。

## 4. 会**静默**失败的 LuaJIT 限制

| 限制 | 症状 | 修法 / 证据 |
|---|---|---|
| **单函数 65535 字节码指令** | 加载时报 `function too long`；加载器**静默跳过整个模组**——日志里什么都没有 | 一个大的位图表构造器真的撞到过。把数据打包成字符串，首次使用时懒解析 |
| **单函数 200 个 local** | `too many local variables` | 面板之所以是一整个大函数就是这个原因（`The whole panel lives in one function: Lua allows 200 locals per function`）；撞到了就拆成闭包或把面板做成方法表 |
| **很早就发起的调用可能卡死游戏** | 一位反馈者的游戏在第 120 帧卡住 | 在 update 线程里 spawn shell / 调 `CreateDirectoryW`。优先用 `ffi` 调用，文件操作只在启动做一次，绝不每帧做 |

字节码上限之所以这么贵，就是因为它**静默**：你得到一个“装好了但什么都不做”的模组。
当一个模组**完全不产生日志行**时，先怀疑这个。

### 4b. 两个纯 Lua 的坑，看起来像引擎的 bug

都是写 `template/panel_skeleton.lua` 时踩到的，都值得记住，因为症状指向引擎而不是你的代码。

**声明在函数下面的 `local`，在那个函数里不在作用域内。** 它能编译通过，名字静默变成
*全局*读取：

```lua
local function frame()
    if count >= FAIL_LIMIT then return end   -- 这里的 FAIL_LIMIT 不是下面那个 local！
end
local FAIL_LIMIT = 5                          -- 太晚了：上面不在作用域
```

`frame` 里的 `FAIL_LIMIT` 是全局，也就是 `nil`，于是 `0 >= nil` 在第一帧就抛
`attempt to compare number with nil`。**Lua 不会有任何警告。** 把上限常量声明在使用它的
函数**上面**；如果某个守卫表现得像一个常量是 nil，先查声明顺序，再去查引擎。

**`local ok, a = pcall(fn, ...)` 会丢掉第一个之后的所有返回值。** 一个返回两个值的引擎
调用于是第二个值永远是 nil，而每一个检查它的守卫都会永久失败：

```lua
local function call(what, fn, ...)
    local ok, a = pcall(fn, ...)     -- resolution() 的第二个返回值没了
    return true, a
end
local ok, w, h = call('Gui.resolution', sr.Gui.resolution)   -- h 永远是 nil
```

症状是永久的 `resolution not numeric` / “引擎从来不按文档返回”——你会跑去重新推导一个
**根本没错**的引擎偏移。把元数（arity）明确写出来
（`local ok, a, b = pcall(fn, ...)`），要加就刻意加；不要用 `select('#', ...)` 糊过去，
那会让调用方的解构变得不安全。

两个坑都被离线测试台（`hd2-offline-engine-harness`）覆盖了——这就是要有测试台的原因：
这些 bug 在代码评审里看不见，在测试里一眼就现。

## 5. 读游戏内存

- **只读已提交、私有、可读的页。** 用 `VirtualQuery`，跳过 `state ~= 0x1000 (MEM_COMMIT)`、
  `prot == 0`（不可访问）和 `prot == 1`（不可访问）。护甲模组扫描时还偏好 `>= 64 KiB` 的页，
  以及首个结构命中附近的 `Hot` 窗口（Armory Forge 则是只遍历首个护甲被动块前后 ±4 MiB，
  而不是整个地址空间）。
- **每次读取都要有界。** 护甲模组的读取器拒绝 `n < 1 or n > 262144`、地址低于 `65536`、以及
  高于 `140737488355328`。把长度交给 `ReadProcessMemory` 之前先夹紧。
- **绝不要写 guard 页。** 写之前读 `VirtualQuery` 的保护字段，直接拒绝任何 `>= 0x100`
  （guarded/noaccess）或 `0`。然后 `VirtualProtect` 改成 RW、写入，并且**还原原来的保护属性**。
  和 guard 页对着干会破坏运行中的引擎状态。
- **用绝对偏移之前先校验 build。** 对模块做哈希（对 `game.dll` 和主模块算 `BCrypt` SHA-256），
  再比对已知代码点的一小段字节签名。不匹配就跳过整个功能，而不是去读一个过期偏移：
  ```lua
  assert(rd(base + 0x14c0350, 16) == unhex('48895c24084889742410574883ec208b'),
         'native presenter changed')
  ```
- **撕裂读是真的。** 读一个值、据它推导，然后在相信结果之前**回头复读源头并比对**
  （护甲模组的语言读取就是这么做的）。
- **`VirtualQuery` 查的是你自己的进程，不是目标进程。** 不带 `Ex` 的形式
  （`VirtualQuery`、`VirtualProtect`）作用于**调用者**的地址空间；跨进程工具必须用
  `VirtualQueryEx(handle, addr, …)` / `VirtualProtectEx(handle, …)`。写错这一点是**静默且自洽**的：
  工具会如实报告"这个页不可读"——只不过是对错误的地址空间——于是探针报 `total writes=0`，
  整轮看起来像个否定的结果。这在实际验证中白烧掉了一轮（`mods/mobility-optimization` 的
  `tools/ability1_live.py` 文档字符串里有记录）。
- **写入需要带写权限的句柄；只读句柄的失败表现是"零次写入"。** 用
  `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` 打开的句柄调不了 `VirtualProtectEx`，
  它需要 `PROCESS_VM_OPERATION`；而 `WriteProcessMemory` 还需要**再加上** `PROCESS_VM_WRITE`
  （`0x0400 | 0x0010 | 0x0008 | 0x0020`）。拿读取器的句柄去走写路径是范畴错误，它不会报
  "权限不足"——它报的是"什么都没写进去"。
- **"这个写入只发生一次"可能是代码路径专属的观察。** 某个状态字节看起来只在按键时写一次——
  直到角色真正**在移动**时，游戏**每帧重算**它，任何一次清零都在约 50 毫秒内被覆盖。
  要验证"N 帧之后我的写入还在不在"，并且在你打算发布的那种条件下验证。
- **校验 id64。** 引擎 id64 很大。护甲模组把任何低于 `2^48` 的捕获值当作
  “像指针或垃圾”直接拒绝；对材质槽它还会顺着指针走（真正的 id64 在 24 字节处），因为给
  `G.material` 喂一个错的 id 会让它返回垃圾 ink，之后在原生层 fault。
- **磁盘上的 `game.dll` 是加壳的：可以哈希它，但不能从它里面读代码。**
  build 25480438 实测（`data/game/game.dll`，15,522,408 字节）：

  | 观察项 | 值 |
  |---|---|
  | 磁盘文件的 SHA-256 | 与 loader 的 `GAME_DLL_SHA` 门禁常量**完全一致** |
  | PE 头解析 | 正常——`PE\0\0`、16 个节、`machine=0x8664` |
  | 主节的**节名** | 被抹成空白 |
  | 承载代码的那个节的香农熵 | **7.9998**（8.0 = 纯随机） |
  | 存在的自定义节 | `.winlice`、`.vm_sec`、`.boot`（解压/引导 stub） |
  | 某个 16 字节代码签名在文件的任意位置 | **不存在** |

  按“白烧时间”排序的结论：

  - **哈希磁盘文件是正确的、有用的。** loader 的版本门禁就是这么做的，所以磁盘 SHA-256 才对得上
    `GAME_DLL_SHA`。指纹核对类检查没问题。
  - **在磁盘镜像上读代码、扫字节签名、或把 RVA 映射成文件偏移，都没有意义。** 那些 RVA 会落在节的
    原始数据之外（虚拟大小远大于原始大小），而那里的字节**不是**进程实际执行的字节。扫文件只会得到
    “签名找不到”，而由此很容易错误地得出“游戏更新了”。
  - **要离线分析代码，先从进程里 dump 出来，再分析 dump。** `melee-vehicle-rescue` 的工具就是正确
    形态：`tools/dump_range.py` 等写出 `research/private/*.bin`，而 `pe_sections.py` /
    `native_xrefs.py` / `raw_strings.py` / `type_tables.py` 读的是这些快照——**从不**读安装目录里的
    那个文件。`c4_input_facts.py` 则是直接扫实时进程内存。两种都对；读安装目录不对。
  - **不要自己尝试脱壳。** 用哈希确认 build，然后从运行中的进程里读你需要的字节。

## 6. 已发布模组的配置 / 数据处理

配置 bug 预防起来很便宜、调起来很贵，因为只有模组自己见过那个文件：

- **严格解析。** 用锚定模式匹配整行（`^%s*rows%s*=%s*(%d+)%s*$`），这样被注释掉或写了一半的
  行不可能静默改变行为。注释要显式忽略。
- **每个数值选项都夹紧**（`math.max(1, math.min(11, v))`）——坏值绝不能到达引擎调用。
- **不要让遗留开关改变行为。** 护甲模组无条件强制 `statrows = true`，因为这个选项已经不再
  控制任何东西，而用户文件里还留着它。
- **永远不要为了塞进上限而截断。** 超限的合并是**被拒绝**；被截断的记录会让游戏 fast-fail。
  给出明确的拒绝信息，胜过一次崩溃。
- **小心地读-改-写配置。** 未知键必须活下来：护甲模组只剥离它自己的 `card.*` 行、重写它们，
  其他每一行原样保留。
- **绝不要在同一帧里又写又读配置**而不清缓存（`M.conf_text = nil`），否则改动要到重启才可见。

---

- **配置解析有两个入口,只修了一个。** 同一份设置既被"分节"解析器读、也被"平铺"解析器读。只改一处会被
  另一处覆盖,于是改动看起来完全无效。动配置解析之前,先把**所有**解析器找齐再宣布修好 —— 这个模组有两个,
  两个都得改(`stratagem-cooldown` 2.9.5 → 2.9.6)。
- **中文取值静默生成了非法键。** `仅载具` / `仅支援武器` / `全部` 这类值解析不出来,配置行写了也被忽略,
  还生成了 `仅vehicles` 这种畸形值。修法:别名表补齐新词并**最长优先**匹配。证据:
  `stratagem-cooldown` `docs/pitfalls-and-fixes.md` §3。
- **未知类别被默认排除。** `in_scope()` 会拒绝任何它不认识的家族(包括 `nil`),所以未来游戏更新新增的战备
  根本不会被修改。把未知家族改为**跟随已有的颜色/开关**,而不是排除(`stratagem-cooldown` 3.8.0)。
  默认放开会响亮地失败;默认关闭会"什么都不做"地失败。

## 7. 让 bug 能被查出来的日志

被修好的模组都有这些；没修好的都没有。

1. **每次状态变化一行**，卡住时每 N 帧一条心跳。不要每帧。
2. **写原因，永远不要只写 “blocked”。** `ui gate blocked: no_ship_markers frame=1832
   world=3 session=false in_session=false markers=0` 是诊断；`ui gate blocked` 是一个求助帖。
3. **把你之后会需要的事实提前记下来**：分辨率、GUI 是否存在、`Gui.is_visible`、ladder 步骤、
   world 数量，以及**每个 world 对象的稳定序列号**——`tostring(world)` 对每个 world 都打印
   `[World]`，根本分不开两个：
   ```lua
   local map = setmetatable({}, {__mode = 'k'})   -- 弱键：不泄漏
   ```
4. **每一次重试资源的首次成功都要记**，一直失败时也要记尝试次数
   （`still missing (try 40) font=nil material=nil`）。
5. **写一个 STATUS 文件**，在面板根本打不开时让用户能发给你（Armory Forge 的
   `ArmoryForge-STATUS.txt`）。如果你的诊断信息只活在一个画不出来的面板里，那它就不存在。
6. 留一个**本地开发驱动**（标记文件加命令文件，例如 `development.enable` + `development.command`），
   这样你能从外部驱动模组，而不是加一个将来会发布出去的热键。标记文件不在时就禁用。

## 8. 看起来能做、其实做不了的事

已经验证过的死路。不要在这些上面花时间。

| 尝试 | 结果 |
|---|---|
| 把屏幕 GUI 分配到另一个 world 里，好让它一直活着 | 原生崩溃 |
| 这套引擎 build 上的材质参数舞 | **即使拿到了正确的 id64** 也在原生层 fault；矩形根本不需要材质——跳过它并如实说明 |
| 把材质 id 设成指针或垃圾值 | `G.material` 返回垃圾 ink，`set_scalar` 之后 fault，`pcall` 一个都抓不到 |
| 实时换配色方案 | 生效了一秒，然后游戏卸载了贴图，护甲变全黑——宁可不上线也不发出去 |
| 只重试一次的资源获取 | 一次早期 NULL 槽位就让整局面板被放弃 |
| 用注入输入关掉星图 / 操作星图 | `Tab` 能开不能关；注入 `Esc`/右键同样无效（见 `hd2-mission-entry`） |

---

- **`tasklist` 的 `/FI` 过滤器区分大小写,大小写写错会被读成"游戏没在运行"。** 进程实际叫
  `helldivers2.exe`,而检查写的是 `Helldivers2.exe`,于是四次报告"游戏没启动",每次都白绕一轮。
  用小写检测;并且把"会卡住整轮工作的进程检查"当作要**记录**的东西,而不是要相信的东西。
- **用 Steam(`-applaunch`)启动,不要直接跑 exe。** 直接运行 `helldivers2.exe` 会让一个约 92 MB 的
  Steam DRM 桩空转,表现为黑屏或卡死,然后被归咎于游戏或某个模组。按 Steam 的方式启动,这个症状就消失。
- **另一类启动崩溃：AutoChat 过早调用 native 本地化。** AutoChat 0.8.0 记录了首次 update 观察日志，之后日志在下一次心跳前结束。代码检查发现，这段期间会批量扫描目录，并在发现记录时调用 native 本地化 thunk。0.8.1 不再为每条发现记录本地化，而是改用带守卫的 `debug_name` 读取，同时保留目录 ID、规则和发现逻辑。由于没有堆栈，无法确定具体访问冲突原因；目前能支持的结论是启动阶段的调用时机有风险，而不是某个已证明的 AV 机制。0.8.1 经标准 Arsenal → Steam 部署后，加载器报告 73 个模组已加载、0 个失败；AutoChat 运行 19,801 帧、0 个错误，观察到 149 个战备条目；按 Space 继续大厅连接弹窗后，游戏到达有角色和完整 HUD 的可交互舰桥。这只验证了该构建与该会话的启动，不代表菜单或消息功能全部通过。

  **发现记录时，不要在隐式批量扫描中调用 native 本地化。** 函数签名有效且调用包在 Lua `pcall` 中，都不能证明 native 回调在该启动阶段安全。发现阶段优先使用带守卫的被动名称读取；只有功能需要显示文本且运行时环境就绪时才解析本地化文本。把 ID 和发现逻辑与显示名称分开，避免备用名称改变匹配规则。不要把此案例推广成禁止所有 native 调用；应分别确认调用目的、时机和证据。

  **离线验证与实机验证要分开。** 离线 LuaJIT/Lupa 回归能证明目录与规则不变量，却不能证明 native 启动路径安全。候选构建启动前，先核对 Arsenal 当前生效层与打包版本及资源声明；随后记录 begin/complete 标记和心跳、加载器已加载/失败数、模组错误/计数行，以及是否到达可交互场景。日志停在 begin 只能标出最后观测到的阶段；没有堆栈时不能据此证明是哪次 native 调用导致终止。
- **模组管理器库里的旧包会覆盖更新的层。** 库里有旧包、磁盘上有手工放好的新层时,点"部署"会用旧包覆盖。
  要么先重新导入新包再部署,要么只用已经放好的那一层 —— 而且最好**同时在飞的包只有一个**。

## 9. 能离线测的部分，就离线测

你没法给引擎写单元测试。但你可以**针对引擎边界**测你自己的代码：

- `lupa`（CPython 里的 LuaJIT）+ 一个会统计 `create_screen_gui` / `destroy_gui` /
  `Gui.move` 调用的假 `stingray` 表，能抓出：保留式重建泄漏、拆除不完整、静止面板却在调
  `Gui.move`、拖拽越界、以及在**没有固定等待**的情况下分级建立能否跑完。
- 用 LuaJIT 编译检查每个源文件，并且断言你期望的 FFI 表面——`hd2-ffi-audit` 就是用它把住构建的。
  你实际调用的符号少了一条 `ffi.cdef` 就是调用点的硬错误，而且这曾经是一个发布出去的 bug：
  `missing declaration for symbol 'VirtualAllocEx'` 才是“点击卡片没反应”的真因。
- 也要断言**数据不变量**，不只是代码：每个标签在你的点阵字体里都必须有字形；每个英文名都
  必须和原生 id 对得上；任何描述都不能超过面板宽度。

在功能还小的时候就把这些写上。等崩了之后再补，会慢得多。

---

- **你自己的检查脚本可能就是那个说谎的东西。** 一次部署校验按 `.patch_0` 过滤,而实际部署的文件叫
  `.patch_323`,于是它报告"游戏目录里 0 个层" —— 把排查引向了一个其实完全正确的部署。改为**按内容匹配**
  并做 **sha256 逐字节比对**,不要相信文件名模式。
- **断言了已废弃行为的测试会失败,而产品是对的。** 一个单元测试在"把百分比吸附到 100/80/50"这个行为被
  按要求移除很久之后还在断言它,于是测试由绿变红指向了测试本身而不是代码。移除一个功能时,在同一个提交里
  就去测试里搜它。替换后的断言描述的是新契约:"自由数值原样使用,越界钳制"。
